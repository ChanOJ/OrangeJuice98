PC Mega Demo Project (v0.03e)

What is this about ?

The goal of this project is to realize an ST-like megademo on PC. More precisely, there is a "menu" (which looks like a demo effect) and the users selects the "part" he wants to see. Each of theses parts is written by a separate demo group. Any group can participate by writing a part.

The goal is not to write parts looking like ST effects but powerful PC ones. Of course, "smiley" parts will be accepted, though. A part is not a demo but a technical "screen" containing as many effects as possible. You can for example mix 2D and 3D effects or anything you want. No between-effects design, no sound synchronization, only an effect that can loop until the user presses a key. Then, the menu is launched again and let's go for another part ! Atari ST Megademo parts worked like that.

Now, I must tell you that you can do all you want. If you want to put multi-part, with between-effects... We want you to participate in this megademo, so you are free!

What will happen ?

In a first step I'll collect the name of groups interested in the project, wether it is in order to write a part, the main menu, modules, graphics or anything else. Just send me a mail (address is at bottom of this text). You must subscribe to the megademo mailing list if you want to know all news about specifications. All messages must pass by the mailing list. To subscribe, just go to this web page: www.onelist.com/subscribe.cgi/megademo Register you and that's all. You could receive all old mails that are sent before your registration.

Meanwhile, Xann and me will develop the common library routines. They will be modified as decisions are taken by everybody. All comments and ideas will be welcome. You can already start writing a part, but we would prefer you wait for things to be more fixed and everybody is ok.

After the Wired (mid-july), serious things will start. Coders will be able to start writing their part because debugging functions will be available.

The goal is to finish all parts before the end of the summer holidays (about the end of september will be cool :) ).

For coders !

Programming constraints may be modified depending on future discussions.

  • OS would be DOS (try to imagine it is an OS)
  • language would be Watcom C
  • common library routines will be used (memory/file/video/sound management)
  • perhaps common PictureFileReader could be cool. no?
  • Files will be compressed, packed and crypted in the final lib version. So don't waste your time to code .PNG reader library, uncompressed .BMP format will be enough, .RAW format too!
  • video modes would be limited. We have to decide which modes are the best. I would like to have fewer modes as possible. around 4 modes will be cool: lowres-lowcolor, lowres-highcolor, highres-lowcolor, higthres-hightcolor
  • sound management will probably be done using FreddyV's usmplayer
  • datas part size will be limited to 500KB/1MB depending on part number
  • you don't have to give us the sources, but only one or several .OBJ file(s)
  • the full demo will consist of one .EXE file (containing all the .OBJ ones) and one packed archive file (containing all data files) for each part. This will make possible to look at some parts even if some data files are corrupt or missing. Each group will send one or several .OBJ file(s) together with a .H file containing the prototype of the main function to call. There are 2 main rules to follow in order to make possible the linking of all parts :
  • declare as "static" as many global objects (variables, functions) as you can. This will allow two different groups to use for eg. functions with the same name. Of course, your main function must not be defined as static.
  • avoid usage of statically allocated global arrays (allocate them with Malloc() instead). If you use constant data in a global array, load the data from a file after having allocated the array.

For everybody !

We will be obliged to fix a size limit for each part. Modules must be as small as possible. The size limit will be applied to compressed size, which means you can use raw pictures files without any problem because they will be crunched in the final archive file.

What we need to decide !

The most important thing is to agree about what common functions we have to provide the coders. All parts will have to use the same library. This will allow us to handle problems more easily and will reduce the full demo code size and decrease bug number for these parts.

One of the goals is to keep the library as small and as simple as possible. See all .TXT files in the lib directory for more precise information.
